## Sammanfattning

P3.4 levererar ett komplett mätinstrument för postgres-vs-openEHR-paritet i FHIR Facade: kanoniseringsregler per FHIR-resurstyp, persistens i `parity_snapshots`-tabell, audit-events på `core.audit.access`, JSON+Markdown-export via tre nya endpoints, dashboard-visualisering med linjegraf och tabell, samt en veckovis schemalagd körning med första aktiva mätpunkt 2026-05-10. Sprint 2 openEHR-spår är därmed levererat. P3.4 möjliggör mätbar styrning av P3.0b:s effekt — varje XML-OPT-bridge-bidrag ska efter denna fas reflekteras som minskad mismatch i trend-vyn över tid.

## Vad fungerar

- ✅ **Paritetsmätning** per patient + aggregat över alla patienter i `openehr_ehr_cache`
- ✅ **6 FHIR-resurstyper** kanoniserade enligt `KANONISERING_VERSION=1` (Patient/Observation/MedicationStatement/Procedure/Condition/AllergyIntolerance)
- ✅ **Persistens** i `parity_snapshots`-tabellen med CHECK-constraints på `trigger` och `resource_type`, idempotent via fil-närvaro-versionerad migration
- ✅ **PARITY_RUN audit-events** på `core.audit.access` med `actor.hsa_id='system:parity-runner'`, schema-paritet med audit-mw-events (AC19)
- ✅ **3 endpoints på app-nivå:** `POST /facade/parity/run`, `GET /facade/parity/latest`, `GET /facade/parity/history` — alla med `?format=json|markdown` (Path Y, utanför auth/audit/pdl-mw-kedjan)
- ✅ **`<ParityTrend />` dashboard-vy** i `services/dashboard/src/pages/` — recharts linjegraf + tabell + refresh-knapp + state-handling via react-query
- ✅ **Veckovis scheduler** (söndag 02:00 UTC) som kallar `ParityRunner.runForAll('scheduled')`, första kör garanterat ≥ 2026-05-10 02:00 UTC
- ✅ **62 nya unit-tester + 5 scheduler-tester + 1 integration-test för AC19** = 73 totala fhir-facade-tester gröna
- ✅ **CI grön** på alla 7 P3.4-commits (1m3s–1m20s per körning)

## Vad som inte uppnåtts (eller blev annorlunda)

- ⚠️ **Ingen empirisk demonstration av trend ännu.** Alla 18+ snapshots har identiska counts (Patient 0/1, Obs 0/3, Proc 0/1, Med/Cond/Allergy 0/0) — verkligheten är oförändrad sedan dag-0. Linjegrafen är "flat" i Sprint 2-tillstånd; trend blir mätbar först när P3.0b eller materializer-fix introducerar förändring.
- ⚠️ **Path X (separat `serviceAccountBypassMiddleware`) övergavs efter foundation-verifiering.** `/facade/*`-paths ligger redan utanför mw-kedjan i fhir-facade — bypass blev överflödigt. Path Y-pivoten dokumenterades i v2-spec.
- ⚠️ **Materializer-pipelinen flödar 0 rows till FHIR-tabellerna.** Postgres-vägen förblir tom tills antingen P3.0b adresserar EVALUATION-mappning eller en separat materializer-fix triggas. Dokumenterat som öppen punkt utanför P3.4.
- ⚠️ **AllergyIntolerance via openehr returnerar `[]` med `logMissingField`-flagga.** Ingen archetype-mappning i Sprint 2. Adresseras i Sprint 3+ när `adverse_reaction_risk.v1` introduceras. PostgresStore wrappar befintlig `findAllergiesByPatient` för konsistens; openehr-sidan blir N/A för paritetsmätning.
- ⚠️ **CANONICAL_STORE=both är nu default i docker-compose.yml.** P3.3 hade `postgres` som default. Operationellt: andra miljöer som inte vill köra paritetsmätning måste explicit override:a `CANONICAL_STORE=postgres` eller `=openehr`. Ej icke-disruptiv default längre.
- ⚠️ **Visuell rendering av `<ParityTrend />` är inte browser-verifierad** i denna session — TS-build grön, data-pipeline (vite-proxy → fhir-facade → core-db) verifierad via curl, men faktisk Recharts-rendering kräver browser-tools eller manuell granskning för bekräftelse.

## Lärdomar

1. **Path Y-pivoten löste arkitekturell osäkerhet tidigt.** Must-fix-granskningen efter v0-spec fångade att Path X krävde antaganden som inte stämde (`next('route')` med use-mw, `req.auditAction`-override, ny mw-introduktion). Att verifiera mot kod *innan* implementation startar besparade ~2 h kod-skrivande som hade behövt revideras.
2. **Dag-0-mätning före kod gav stabil mätankaret.** Värdet är inte uppenbart i Sprint 2-tillstånd där ingenting förändrats — men det blir kritiskt vid Sprint 3 / P3.0b när mätningar ska jämföras mot ett pre-implementations-baseline.
3. **Smoke-test fångade `classifyRootCause`-bugg som unit-tester inte hade fångat.** Order-bug: `if (p === o) return 'parity'` triggade före `if (p === 0 && o === 0)`-check, vilket klassade 0/0-fallen felaktigt som "parity" istället för "evaluation-blocked"/"no-fixture-data". Test-svit har nu en explicit regression för detta. **Implikation:** smoke-test mot live-stack är komplement till unit-tester, inte substitut.
4. **Deploy-pipeline saknar auto-rebuild på commit.** Manuell `docker compose up -d --build fhir-facade` krävdes i 4.7 för att deploya 4.5+-koden. Operationell hardening-kandidat — t.ex. CI-baserad image-publish + docker compose pull-flöde. Inte P3.4-scope.
5. **CANONICAL_STORE=both ändrades till default.** Tidigare default var `postgres` (icke-disruptiv). Nu är `both` default — fhir-facade kommer alltid kontakta EHRbase vid startup. För miljöer utan EHRbase måste `CANONICAL_STORE=postgres` sättas explicit. Värd att ha med i operations-checklista.
6. **Recharts + react-query + tailwind är dashboard-konventionen.** Verifierades först i 4.7. Tidigare antaganden (single-HTML-fil, CDN-React) var fel. Framtida dashboard-arbete ska anta SPA-Vite-stacken.

## Sammanfattning

P3.1 etablerade `services/openehr-composer/` som första riktiga konsumenten av openEHR-stacken — en TypeScript Express-tjänst som tar emot clinical events över HTTP och skriver compositions till EHRbase via REST. Tjänsten kör end-to-end mot Fru Andersson-scenariot via fixture-templates: 4 event-typer (vitals × 3 + procedure) producerar verifierade compositions; 3 EVALUATION-event-typer (medication, allergi, diagnos) blockeras av att fixturerna saknar EVALUATION-shape och loggas som strukturerade gap för P3.0b.

Sex ytterligare CKM-arketyper hämtades och dokumenterades. Två avvikelser från P3.1-specens namn (`medication_statement.v1` finns inte i CKM-mirror; `adverse_reaction_risk.v1` finns inte — ersatta med närmaste motsvarigheter `medication_summary.v1` respektive `.v2`). Diagnostic-compilern parsar alla 7 ADL utan fel; XML-OPT-output kvarstår P3.0b-arbete.

P3.1-rapporten levererar empirisk data från `gap-tracker.ts` om vilka constraint-typer composern faktiskt använder — direkt input till P3.0b-bridge-design.

## Input till P3.0b — Tre frågor från sektion 8.3 i PHASE-3.0-REPORT.md

### 1. Vilka constraint-typer förekommer i Fru Andersson-flödet?

Empiriskt observerat under composer-körning (alla event-typer aktiverade):

| Constraint-typ | Antal observationer | Användningsområde |
|---|---|---|
| `DV_QUANTITY` | 5 | Vitals (temp, BP, pulse) — magnitude + units |
| `DV_TEXT` | 4 | Procedure description |
| `ISM_TRANSITION` | 4 | Procedure state ("completed") |
| `DV_CODED_TEXT` | (genererat i header, inte direkt registrerat) | Composition `category`, `setting`; ACTION `current_state` |
| `DV_CODED_TEXT` (terminologi-bindings) | 0 i Sprint 2 | Skulle förekomma vid SNOMED/ICD-10/ATC — blockerade av att EVALUATION-events inte mappas |
| `C_DV_ORDINAL` | 0 | Ej använt i composer-shapes vi byggde |
| `OPERATIONAL_TEMPLATE template_overlay` / arketyp-slots | 0 | Fixturerna har inga slots |

**Konkret implikation för P3.0b:**
- Bridge-koden **måste** täcka minst: `DV_QUANTITY`, `DV_TEXT`, `DV_CODED_TEXT`, `ISM_TRANSITION`, `CODE_PHRASE`, `ELEMENT`, `ITEM_TREE`, `HISTORY`, `EVENT`, `ACTION`, `OBSERVATION`, `EVALUATION`, `COMPOSITION`. Det är **~13 RM-typer**, inte 30. Detta minskar Option 1-uppskattningen (2 000–5 000 rader) avsevärt.
- `C_DV_ORDINAL` och `template_overlay` är **inte** kritiska för Sprint 2-täckning — kan skjutas till senare iteration.
- `term_bindings` (SNOMED/ICD-10/ATC) blir kritiskt så snart EVALUATION-events ska mappas — P3.0b **bör** inkludera term_binding-yta från start för att undvika omarbete i Sprint 3.

### 2. Vilka template-features är obligatoriska för EHRbase-acceptans?

Verifierat via 422-iterationer mot live EHRbase 2.30.1:

- **`archetype_details.template_id.value`** — obligatorisk i composition (utan = 422)
- **`archetype_details.archetype_id.value`** — obligatorisk
- **`archetype_node_id`** på alla AOM-noder — obligatorisk (även `at0001`, `at0002`-konstanter måste matcha template-strukturen)
- **`category`** med `defining_code` mot `openehr`-terminologin (kod 433 = "event") — obligatorisk
- **`composer`** med `_type: PARTY_IDENTIFIED` — obligatorisk
- **`context.start_time`** + **`context.setting`** — obligatorisk
- **`language`** + **`territory`** + **`encoding`** — obligatorisk
- **DV_QUANTITY-units enligt template-constraint** — obligatorisk (vår fixture-hard-rule "mm3" är ett exempel)
- **`composition.subject` per content-nod** måste vara `PARTY_SELF` eller matcha EHR-subjektet
- **`term_definitions`** per språk — composer hämtar inte detta, men EHRbase verifierar inte det när `Prefer: return=representation`

**Konkret implikation:** P3.0b-bridge måste i sin första iteration producera kompletta `archetype_details`-block, bevara `archetype_node_id`-träd, och respektera units-constraints. Saknad av något av dessa fält ger 422 från EHRbase.

### 3. Hur stor är fixture-täckningen vs gap?

Fru Anderssons sju event-kategorier per P3.1-spec:

| Event-typ | Mappad via fixture | Gap-anledning | Sprint 2-status |
|---|---|---|---|
| `core.clinical.observation.vitals.body_temperature` | ✅ time_series.en.v1 | Units degraderade till mm3 | **Funktionsdugligt** (med placeholder-units) |
| `core.clinical.observation.vitals.blood_pressure` | ✅ time_series.en.v1 | Units degraderade + saknar separat SYS/DIA | **Funktionsdugligt** (förenklad) |
| `core.clinical.observation.vitals.pulse` | ✅ time_series.en.v1 | Units degraderade | **Funktionsdugligt** |
| `core.clinical.procedure.completed` | ✅ minimal_action.en.v1 | Saknar body_site/method/equipment | **Funktionsdugligt** (förenklad) |
| `core.clinical.medication.prescribed` | ❌ | EVALUATION-shape saknas i fixtures | **Blockerad** (gap-loggad) |
| `core.clinical.allergy.reported` | ❌ | EVALUATION-shape saknas | **Blockerad** |
| `core.clinical.condition.diagnosed` | ❌ | EVALUATION-shape saknas | **Blockerad** |

**Sammanfattning:** **4 av 7 event-typer (57 %) är funktionsdugliga via fixtures.** 3 är blockerade — alla EVALUATION-events.

**Konkret implikation för P3.0b:**
- Eftersom täckning är 57 %, närmare 50 % än 80 %, bör P3.0b **inte** designas för "complete the gap".
- P3.0b bör starta med **EVALUATION-bridge-prio**: producera XML-OPT från `medication_summary.v1`, `adverse_reaction_risk.v2`, `problem_diagnosis.v1`. Det löser tre blockerade event-typer i ett svep.
- Vitals och procedure kan parallellt få egna kompilerade OPT som ersätter fixturerna (rätt units, rätt body_site, etc.) men har **lägre prioritet** — fixtures fungerar funktionellt.

## Nästa steg

Beslutspunkt enligt P3.1-spec sektion 8:

- **Om P3.0b prioriteras:** kör P3.0b först — fixture-units-degraderingen och EVALUATION-blockeraringen löses, vilket gör Fru Andersson-flödet komplett. Med constraint-data från denna rapport är scope tydlig (~13 RM-typer + term_bindings).
- **Om P3.2 (Kafka-integration) prioriteras:** kör P3.2 — composern är redo att läsa från Kafka istället för HTTP. Gap-flöde i produktion ger ännu mer empirisk data till P3.0b senare.
- **Parallellt:** CKM-licens-research enligt PHASE-3.0-REPORT.md sektion 8.2.1 kan köras separat — blockerar inte teknisk fortsättning.

**Min rekommendation:** P3.0b nästa, med Option 1 begränsad till de 13 RM-typer denna rapport identifierat. Gör Fru Andersson-flödet komplett innan vi skalar till Kafka i P3.2 — färre rörliga delar att felsöka samtidigt.

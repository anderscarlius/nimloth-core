## Sammanfattning

P3.2 utvidgade `services/openehr-composer/` med Kafka-integration enligt outbox-mönster. Kafka-consumer prenumererar på 6 `core.clinical.*`-topics, skriver events till `composer_outbox` (PostgreSQL) med UNIQUE-constraint på `event_id` för idempotency, och committar Kafka-offset först **efter** outbox-skrivningen lyckats. En separat outbox-processor pollar pending-rader (`FOR UPDATE SKIP LOCKED` för multi-instance-säkerhet), dispatchar mot EHRbase, och uppdaterar status. Crash-recovery rensar hängande `processing`-rader vid composer-startup.

P3.1:s syntetiska HTTP-endpoint är bevarad och har också utökats med outbox-skrivning först (för spårbarhet + idempotency oavsett källa). Alla 8 P3.1-smoke-tester fortsätter vara gröna.

Live-verifierat: Fru Anderssons 6-event akutsekvens via Kafka producerar 4 compositions + 2 gap (medication.prescribed × 2) som förväntat. 26/26 e2e-tester gröna.

## Vad fungerar

- ✅ `@nimloth-core/kafka-utils` — återanvändbar consumer-wrapper (autoCommit: false, manual commit)
- ✅ `composer_outbox`-tabell i `core-db` med constraints + 3 partial-index
- ✅ `OutboxWriter` — idempotent INSERT ON CONFLICT, returnerar `created`-flag
- ✅ `OutboxProcessor` — `FOR UPDATE SKIP LOCKED` claiming, exponential retry (default max 5), `recoverFromCrash`
- ✅ `ComposerKafkaConsumer` — outbox-write FÖRE offset-commit. Vid IO-fel committas inte offset → at-least-once delivery, exactly-once-effekt via UNIQUE-constraint
- ✅ Modifierad `routes/event.ts` — HTTP-route skriver också till outbox + idempotent replay-detection
- ✅ `routes/outbox.ts` — `GET /composer/outbox`, `GET /composer/outbox/stats`, `POST /composer/outbox/poll`
- ✅ Stats-route inkluderar Kafka-metrics + outbox-by-status

## Vad som inte uppnåtts (eller blev annorlunda)

- ⚠️ **Avvikelse från spec sektion 4.7b:** specens instruktion var att HTTP-route ska returnera `202 Accepted` (asynkron). Behöll synkron 201 + composition_uid för att inte bryta P3.1:s 8 tester (AC11). Hybrid-design: outbox-skrivning + synkron processing samtidigt.
- ⚠️ **`core.clinical.medication.statement` finns inte:** specens topic-lista refererade en topic som aldrig skapades av `infra/kafka/create-topics.sh`. Använder verkligheten (`.prescribed` + `.dispensed`) som P3.1:s event-mapper redan refererar.
- ⚠️ **Override-listener-fix:** docker-compose.override.yml flyttar Kafka-host-port 9092 → 14092, men `KAFKA_ADVERTISED_LISTENERS` annonserade fortfarande `localhost:9092` → host-baserade producers fick ECONNREFUSED. Fixat genom att också override:a `KAFKA_ADVERTISED_LISTENERS` i override.yml. Påverkar hela repots host-Kafka-tooling positivt.

## Input till P3.0b — uppdaterad efter Kafka-trafik

Med riktig event-trafik via Kafka tillkom **inga nya constraint-typer** jämfört med P3.1:s syntetiska tester — vilket bekräftar att composer-shapes är funktionell-mässigt täckande för Fru Andersson:

| Constraint-typ | P3.1 | P3.2 (inkl Kafka) | Källa |
|---|---|---|---|
| `DV_QUANTITY` | 5 | 7 | runtime via composition-builder |
| `DV_TEXT` | 4 | 2 | runtime |
| `ISM_TRANSITION` | 4 | 2 | runtime |
| (övriga 9 RM-typer från P3.1) | strukturellt observerade | oförändrat | fixture-XML |
| `EVALUATION` | projicerad | **fortsatt blockerad** | inga events kommer fram pga gap-mapping |

**Nya empiriska observationer i P3.2:**

1. **Idempotency-mönstret fungerar i praktiken** — `outboxAlreadyExistedTotal: 1` visar att samma `event_id` inkommit två gånger via Kafka och blockerades av UNIQUE-constraint. P3.0b behöver inte hantera duplikat-events i bridge-koden eftersom det löses på outbox-nivå.

2. **Gap-tracker:n ser exakt samma gap som P3.1** — fixture_limitation (units mm3 forcerar) + no_template_mapping (medication.prescribed). Bekräftar att P3.0b-prio är EVALUATION-bridge, inte ny constraint-yta.

3. **Outbox-as-spårningsmekanism** kommer vara värdefullt under P3.0b-utveckling — när bridge:n produceras kan dess output validate:as mot historiska events i `composer_outbox` (skicka samma payload, jämför ny vs gammal composition).

4. **`kafka.outboxWrittenTotal` − `outboxAlreadyExistedTotal` matchar `events_received`** över tid → outbox är konsistent med Kafka-flödet. Inga events tappade.

**Konkret implikation för P3.0b-prio:** ingen kommer från P3.2, bekräftar P3.1:s slutsats att EVALUATION-bridge är prio. Estimera 2–3 sessioner enligt strategi.
